# 协作规范

## 1. 目的

本文档用于约束项目协作开发边界，统一任务执行、提交记录和跨模块修改流程，避免误改他人模块、接口理解不一致、提交不可追溯等问题。

## 2. 协作边界

### 2.1 分工原则

- 每位成员优先只修改自己负责目录内的文件。
- 对方负责目录内的文件只允许阅读，不允许直接修改。
- 公共目录或公共配置的修改需要先说明影响范围，再由相关成员确认。
- 与当前任务无关的“顺手修复”不应混入同一次修改。

### 2.2 责任目录

项目启动或分工调整时，应填写并维护以下映射：

```text
成员A（YuzhSong）负责目录：<frontend、model-service、docs、README.md>
成员B（7nfc）负责目录：<backend、database>
共同维护目录：.gitignore
```

如果某次任务的实际责任范围与上面不同，应在任务描述中单独说明。

### 2.3 禁止事项

- 未经确认直接修改对方负责目录下的文件。
- 未经确认重构公共基础代码、接口契约或数据结构。
- 删除他人文件、批量改名、变更目录结构且未提前说明。
- 修改与当前任务无关的模块、页面、接口或配置。
- 在未更新文档的情况下修改接口、数据表、启动方式或模块职责。

### 2.4 跨边界修改流程

当任务必须跨目录修改时，按以下流程执行：

1. 说明跨边界原因。
2. 列出需要修改的文件。
3. 说明预期影响和可能风险。
4. 等待目录负责人或项目负责人确认。
5. 修改完成后，在提交说明中标记 `cross-boundary`，并单列跨边界变更清单。

## 3. 开发前检查

开发前必须先阅读：

1. `README.md`
2. `docs/README.md`
3. `docs/collaboration.md`
4. 与本次任务相关的专题文档，例如 `docs/product.md`、`docs/architecture.md`、`docs/api.md`、`docs/deployment.md`

开始修改前还需要确认：

- 本次任务目标是什么。
- 允许修改哪些目录和文件。
- 是否涉及接口、数据库、启动方式或公共配置。
- 当前工作区是否已有他人未合并或未提交的改动。

## 4. 代码修改原则

- 只做与任务直接相关的最小改动。
- 不删除现有功能，不改变无关逻辑。
- 不擅自升级依赖或重构架构，除非任务明确要求。
- 修改接口、数据结构、部署命令时，同步更新对应文档。

## 5. 注释与修改记录

- 新增或复杂逻辑需要中文注释，说明“做什么、为什么做”。
- 关键函数应说明函数作用、输入输出和异常行为。
- 每次任务应在提交说明或变更说明中提供：
  - 修改人
  - 修改日期（`YYYY-MM-DD`）
  - 修改目的
  - 影响文件列表
  - 验证方式与结果

推荐记录模板：

```text
[修改记录]
修改人：<姓名>
修改日期：<YYYY-MM-DD>
任务说明：<一句话>
影响文件：<文件1, 文件2, ...>
验证结果：<通过的命令/页面/接口>
```

## 6. 生效规则

- 本文档默认对项目所有协作者生效。
- 若与临时口头约定冲突，以本文档和最新书面分工为准。
- 本文档更新后，成员应在下一次任务开始前确认版本一致。
