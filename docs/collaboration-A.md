# 文档A：协作边界与 Codex 提示词规范

## 1. 目的

本文件用于约束双人协作开发边界，统一 Codex 使用方式，避免误改他人模块、风格不一致、提交不可追溯等问题。

## 2. 协作边界（强制）

### 2.1 分工原则

- 每位成员只能修改自己负责目录内的文件。
- 对方负责目录内的文件只允许阅读，不允许修改。
- 公共目录的修改需要双方确认后执行。

### 2.2 责任目录（按实际填写）

请在项目启动时填写以下映射，并在分工调整时同步更新：

- 成员A负责目录：`<填写目录列表>`
- 成员B负责目录：`<填写目录列表>`
- 公共目录（需协商修改）：`docs`、`README.md`、`.gitignore`、`database`（如有共同维护）

### 2.3 禁止事项

- 未经确认直接修改对方负责目录下任意文件。
- 未经确认重构公共基础代码。
- 删除他人文件、批量改名、变更目录结构且未提前说明。
- 为了“顺手修复”修改与当前任务无关的模块。

### 2.4 跨边界修改流程

当任务必须跨目录修改时，按以下流程执行：

1. 在任务描述中明确“跨边界原因”和“影响文件”。
2. 由目录负责人确认后再修改。
3. 提交信息中标记 `cross-boundary`。
4. 在 PR 或提交说明中单列跨边界变更清单。

## 3. 开发与注释规范（通用）

### 3.1 开发前检查

- 必须先阅读：`README.md`、`docs/api.md`、`docs/deployment.md`、本文件（文档A）。
- 明确本次任务边界：只改哪些目录、哪些文件。
- 先看当前分支状态，避免覆盖他人未合并改动。

### 3.2 代码修改原则

- 只做与任务直接相关的最小改动。
- 不删除现有功能，不改变无关逻辑。
- 不擅自升级依赖或重构架构（除非任务明确要求）。

### 3.3 注释与修改记录

- 新增或复杂逻辑需要中文注释，说明“做什么、为什么做”。
- 关键函数应补充函数作用、输入输出、异常行为说明。
- 每次任务需在提交说明或变更说明中提供：
  - 修改人
  - 修改日期（`YYYY-MM-DD`）
  - 修改目的
  - 影响文件列表
  - 验证方式与结果

推荐在文档或提交描述中使用以下记录模板：

```text
[修改记录]
修改人：<姓名>
修改日期：<YYYY-MM-DD>
任务说明：<一句话>
影响文件：<文件1, 文件2, ...>
验证结果：<通过的命令/页面/接口>
```

## 4. 标准提示词模板（母版）

以下为通用模板，不区分前端/后端/算法领域。组员可直接复制后替换占位符。

```text
你是我的项目协作开发助手。请严格遵守以下规范执行任务。

[基础上下文]
- 项目名称：非机动车智能违法监管与服务平台
- 仓库：smart-ebike-violation-platform
- 当前任务：{在这里填写任务目标}
- 当前负责人：{成员姓名}
- 允许修改目录：{目录列表}
- 禁止修改目录：除“允许修改目录”外的所有目录

[强制规则]
1. 开发前必须先阅读并遵守以下文档：
   - README.md
   - docs/api.md
   - docs/deployment.md
   - docs/collaboration-A.md（文档A）
2. 只能修改“允许修改目录”中的文件；其他目录只读不可改。
3. 若实现任务必须跨边界修改，先停止并输出：
   - 跨边界原因
   - 需要修改的文件
   - 预期影响
   等待我确认后再继续。
4. 保持最小改动原则：不改无关代码，不做无关重构，不删除现有功能。
5. 所有新增说明与关键注释使用中文；关键函数需说明作用、输入输出和注意事项。
6. 完成后输出：
   - 修改文件清单
   - 每个文件的改动目的
   - 修改人和日期
   - 验证步骤与结果

[输出格式要求]
- 先给执行计划，再实施。
- 实施完成后给出可直接提交的变更摘要。
- 若遇到阻塞，明确阻塞点和可选解决路径。
```

## 5. 让 Codex 先“生成专属提示词”的模板

下面这段用于让组员的 Codex 根据“标准母版 + 当前任务”先生成一份专属提示词，再把该专属提示词交给新的 Codex 直接开发。

```text
请基于 docs/collaboration-A.md（文档A）中的“标准提示词模板（母版）”，
结合我的当前任务，生成一份可直接用于开发执行的“专属提示词”。

我的输入如下：
- 当前任务：{填写任务}
- 当前负责人：{成员姓名}
- 允许修改目录：{目录列表}
- 禁止修改目录：{目录列表或“除允许目录外全部”}
- 额外要求：{例如“优先不改接口定义”“必须保留现有页面行为”等}

生成要求：
1. 必须保留“先阅读文档A”的强制要求。
2. 必须包含边界控制与跨边界停机确认机制。
3. 必须包含中文注释和修改记录要求。
4. 不要加入具体技术领域实现细节（不要限定前端/后端/算法做法）。
5. 输出的专属提示词应可直接复制给一个新的 Codex 使用。
```

## 6. 实际使用流程（组员视角）

1. 阅读本文件（文档A），确认自己的“允许修改目录”。
2. 把“第5节模板”发给当前 Codex，并填入本次任务信息。
3. 获取生成后的“专属提示词”。
4. 将该专属提示词直接发给新的 Codex，进入正式开发。
5. 开发完成后按“修改记录模板”提交结果并发起协作审核。

## 7. 生效规则

- 本文件默认对项目所有协作者生效。
- 若与临时口头约定冲突，以本文件和最新书面分工为准。
- 本文件更新后，双方应在下一次任务开始前确认版本一致。
